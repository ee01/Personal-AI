# 类人脑项目分析系统

*最后更新: 2026-05-18*

## 当前定位

类人脑项目分析系统是 Personal AI 的项目知识工作台：它把网页感知、实体记忆、项目仪表盘和主动提醒串起来，让用户能从聊天、网页、Slide、Jira 线索中沉淀项目上下文，再回到一个可操作的项目视图。

当前最完整的用户入口是：

- `memory-exploring.html`：查看实体、主题、项目相关记忆。
- `project-dashboard.html`：查看项目鱼骨时间线、里程碑、任务、Jira 链接、健康摘要和决策依据。
- Web Intelligence / Context Recall：在网页或会话场景里提示相关记忆。
- Memory Service：提供实体、召回、关注项目、通知、反思等后端能力。

## 已实现能力

### 感知层

- RingCentral / 网页内容脚本会抽取上下文，并通过 Memory Service 做相关记忆召回。
- Web Intelligence 会基于用户画像、项目关键词、页面内容进行轻量项目相关性判断。
- Google Slides Analyzer 可以从 Slides 表格/文本里识别项目状态并生成更新建议。

### 记忆层

- Memory Service 已提供实体、记忆、召回、关注项目、通知中心等 HTTP API。
- `memory-exploring` 负责把 Topic、Project、Person 等实体以列表/详情方式展示。
- 项目相关网页提示会回链到 `memory-exploring.html` 的稳定深链。

### 项目分析层

- `project-dashboard.html` 当前使用 React 鱼骨时间线展示项目。
- 支持新增项目、新增任务、编辑任务、关联 Jira、导入/导出 JSON 报告。
- 新增项目时会保留用户配置的里程碑，并把仪表盘数据持久化到 `chrome.storage.local`。
- 每个项目卡片会前置健康摘要：完成数、阻塞数、过期任务、近 7 天到期任务和下个里程碑。
- 每个项目卡片会展示决策依据：阻塞、过期、近 7 天到期、缺 ETA、缺 Jira/平台来源等信号会聚合成建议下一步。
- 今日焦点和项目内优先处理项会显示活动级风险分，按阻塞、过期/临期、来源缺口、平台阻塞和临近里程碑解释为什么该任务排在前面。
- 今日焦点下方会集中显示证据补全队列，把缺 ETA、缺 Jira/平台来源的活动任务变成可点击的修复入口。
- 任务详情会显示证据修复面板，直接指出 ETA、来源和风险驱动是否完整；平台状态、平台负责人或平台 Jira 会被统一计入“平台来源”，并可从面板直接定位到 ETA 或来源输入区。
- 每个项目可先预览状态更新草稿，再复制发送；草稿按健康摘要、里程碑、阻塞/过期/近期到期任务和证据来源组织。
- 状态更新草稿预览支持直接编辑审阅稿、恢复生成稿、再复制发送，避免把规则化摘要未经人工确认地转发给团队。
- 状态草稿预览会列出可追溯证据，包括本地任务状态 / ETA、关联 Jira、平台状态和下个里程碑，避免把规则化摘要误当成不可审阅的自动结论。
- 状态草稿复制并标记复核后，会即时刷新复核证据和下次复核提示，避免用户继续看到旧的“未复核/复核过期”判断。
- 证据覆盖不完整的项目会进入“需关注”视图；证据严重不足时给出警示，证据部分缺失时作为轻量关注项处理。

### 决策层

- 当前以用户可见的健康摘要和通知中心为主。
- 自动风险预测仍是后续方向；现阶段只做规则化提示，不自动替用户改项目计划。
- 项目仪表盘中的数据源检查入口会展开 Jira、GitHub、Confluence 的接入状态、未接入原因和下一步，避免把本地工作台数据误认为外部系统权威快照。

## 本轮调研结论

- Atlassian Jira / Rovo 强调把 AI 风险评估放进工作项上下文里，给出风险等级、证据和缓解建议，同时保留人工审批；相似历史、回滚计划和变更上下文是风险解释的重要输入。
- Asana 项目状态更新强调“先给项目健康状态，再附上里程碑、过期任务、图表和统一模板”；Smart Status 也要求用户在发布前审阅 AI 草稿。
- Microsoft Planner 的高级计划能力把依赖、报告、Timeline/Gantt、关键路径、目标和 Copilot 放在同一项目管理路径里；Linear / GitHub 的项目更新也强调项目健康状态、概览和历史更新。
- 业内产品和论文都把“可访问的数据源”视为风险判断前提；本轮把 Jira、平台状态和平台负责人统一成任务来源证据，并在详情页暴露修复动作，而不是只在项目级摘要里报缺口。
- 软件项目风险预测与风险校准论文说明，风险视图至少应把阻塞、过期、近期到期、相似历史和影响因素结构化呈现，后续再接模型预测；当前先落地可解释证据清单。
- Activity Risk Index 与项目风险基线研究提示，风险不只属于整个项目，也应落到具体活动/任务；当前仪表盘先落地规则化活动风险分，用于排序和解释，不把它包装成模型预测。
- Jira 集成自动化研究强调有界自动化：结构化上下文、重新校验、恢复路径和人工审阅门槛比“全自动”更可靠。
- 本轮补充的证据补全队列延续这些结论：先暴露影响判断的缺口和下一步修复动作，再让用户进入任务详情补齐，而不是把低质量数据直接包装成风险结论。
- 本轮继续压缩证据修复路径：缺口面板不只提示“缺什么”，还提供到具体输入区的快速入口，降低用户从风险摘要跳到可执行修复动作的摩擦。

## 当前边界

- 项目仪表盘数据仍是扩展本地维护的工作台数据，不是 Jira/GitHub/Confluence 的权威快照。
- “数据源检查”当前只展示接入准备状态，不读取真实 Jira/GitHub/Confluence；真实多源同步需要进一步接入外部 API。
- 健康摘要、活动级风险分和决策依据是可解释规则，不是 ML 风险模型。
- 平台状态目前仍是本地手动维护的来源证据；它能减少“缺来源”误报，但不能替代未来真实 Jira/GitHub/Confluence 同步。
- Memory Service 的关注项目 API 与前端鱼骨仪表盘还没有完全合并成同一个数据源。

## 下一步建议

1. 把项目仪表盘的本地项目与 Memory Service watched projects 做双向同步。
2. 为健康摘要和决策依据增加真实来源证据，例如最近会话、Slides 更新建议和 Jira 评论。
3. 在状态更新草稿里继续补充真实来源引用，并保留人工审阅门槛。
4. 对接真实 Jira 数据后，再引入风险预测评分，避免在数据质量不足时给用户过度自动化结论。
