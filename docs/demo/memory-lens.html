Memory Lens · 浮窗信息层级重设计

当前右下角浮窗只把「标题 + footer 一行」摆出来，缺乏层次；7 个操作按钮平铺占了卡片大半面积。本稿基于真实从 10.32.56.212 召回的三组 RC 对话，重新按「为什么相关 → 它说了什么 → 我能做什么」三层组织信息，控制操作折叠为 2 个 icon。

所有 mock 来自一次真实 POST /api/v1/context-recall，三组对话各 5 条命中，全部 displayPriority=p1——这本身就是当前 gating 过松的直接证据。

浮窗要回答哪三个问题？

设计目标

用户瞄一眼就能回答下面三个问题，回答不了任何一个就不打扰。

当前浮窗实际呈现 问题

  • 标题常常是 "时间" 或 "@Esone Qiu wrote:"，没有信息量
  • 「为什么相关」只写「向量 命中 网页上下文」，不可解释
  • metadata.summary（LLM 摘要）、actions[]、replyAdvice 全部藏着没有露出
  • 7 个操作按钮平铺：在记忆中查看 / 有用 / 不相关 / 允许此站点 / 今天不提示 / 永久不提示此页 / 永久不提示此站点
  • 所有候选 displayPriority=p1，看不出强弱

重新设计回答三个问题 目标

  • 为什么相关？ → Why-row chips：同群 · Sophia · hackathon，无具体重合不显示
  • 它说了什么？ → 用 metadata.summary（LLM 描述），2 行抓住要点
  • 我能做什么？ → 结构化行动项 actions[]（assignee · deadline）+ replyAdvice
  • 控制操作收进 2 个 icon：右上角 ↗（跳转原文）+ ⋯（屏蔽/静默），thumb 反馈留在底部
  • 多候选时 1 / N 翻页，避免单条不准时无路可走

实现要点

落地建议

前端先做（不动 API） P0

  • 在 selectPrimaryContextRecallMatch() 之后增加 overlapAudit(scene, match)：抽取 metadata.entities.people / topics / groupId 与 scene 求交集；无任何交集降为 hidden。
  • 标题优先用 metadata.summary（LLM 描述），过滤 "@xxx wrote:" / "3. 行动指南" 等结构性前缀；摘要同样用 metadata.summary。
  • 行动项取 metadata.actions[0]，格式 @assignee · description · deadline；无 actions 时用 replyAdvice。
  • 7 个按钮折叠：thumb up/down 保留在 foot，屏蔽/静默/允许站点放进 ⋯ popover。
  • 候选 ≥ 2 时显示 1/N 翻页器。
  • 跳转原文改为右上角 ↗ icon，对应 exploreLink。

后端配合（schema 扩展） P1

  • 在 ContextRecallMatch 显式返回 relevanceTier: 'strong' | 'possible' | 'weak'，前端不再靠 score 数字反推。
  • 返回 overlapSignals: {kind, value}[]，前端直接渲染 chips，无需再做实体抽取。
  • displayPriority=p1 必须要求：同源 groupId/conversationId 命中，或 person + concrete topic 双重命中；纯语义高分最多 p2。
  • 负反馈 recall_quality: negative 时一并写入 {scene_anchor_signature, match_source_cluster}，让「Hackathon/Codex 场景不再拉 Gary trip」这种降权可学习。
  • 广播/公告类消息（HR Open Day / Everyone AI Campaign）增加 broadcastFlag，无锚点重叠时自动排除出 auto_peek。
