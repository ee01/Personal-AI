# 决策中心降噪与分流改造方案

## Summary
- 先按现状定性：服务器上当前 `pending = 53`，全部是 `category = evidence_resolution`、`priority = normal`，且选项几乎固定为“继续查证 / 先记录当前结论 / 暂不处理”。
- 这 53 条里，绝大多数不是“必须你拍板”的决策，而是“证据不足后的人工分流项”。
- 结构化判断结果：约 37 条属于“未来是否会变化/是否有计划”的观察型问题，约 9 条属于“负责人/时间表/上线时间”等信息缺口，0 条呈现为真正的二选一业务决策。
- 现有问题不是“数量太多”，而是“错误地把低价值不确定性升级成 pending 决策”，再叠加弱去重、无老化、无观察池，最终把决策中心变成了 backlog。

## Key Changes
### 1. 先改语义：把 `confirm_request` 从“缺口容器”收缩为“真正需要人决定的项”
- 仅以下情况允许进入主决策队列：
- `property_change` / `profile_conflict` / `openclaw_delegation` / 需要审批的写操作。
- 需要你在两个以上真实分支中选方向，且不同答案会触发不同后续动作。
- 存在明确时效性，且系统没有安全的自动只读查证路径。
- `evidence_resolution` 默认不再直接进入 `pending`；先经过分流判定，结论只能是三类：
- `decision`：确实要你拍板。
- `auto_verify`：系统可自动做只读外部查证。
- `watch`：只是需要持续观察，不需要立刻人工决策。

### 2. 在 `EvidenceResolutionPlanner` 增加“是否需要人工决策”输出
- 扩展 planner 输出字段：
- `disposition: 'decision' | 'auto_verify' | 'watch'`
- `reasonCode: 'authority_required' | 'approval_required' | 'future_monitoring' | 'owner_eta_gap' | 'artifact_gap' | 'time_sensitive_blocker'`
- `sourceAnchor: string`
- `gapType: 'future_monitoring' | 'owner_eta' | 'artifact_check' | 'decision_blocker'`
- 判定规则固定如下：
- 有外部线索且允许只读访问时，优先 `auto_verify`，不进决策中心。
- 问题本质是“未来会不会变”“是否有未披露计划”“是否会调整/迁移/重命名”这类观察型推测时，进入 `watch`。
- 问题本质是“负责人是谁/上线时间何时/具体进展如何”这类缺口时，若没有明确审批动作，也进入 `watch`。
- 只有当答案会改变执行分支或需要你的授权时，才给 `decision`。
- `ask` 场景改为更严格：
- 用户主动查询但证据不足时，默认返回“当前结论 + 缺口 + 系统下一步建议”，不创建决策卡。
- 只有用户明确要求“帮我决定怎么做”或后续动作涉及审批/写操作时，才创建 `decision`。

### 3. 给 `confirm_requests` 增加正式的分流与老化模型
- 数据模型新增字段：
- `routing: 'decision' | 'watch'`
- `reason_code: string`
- `source_anchor: string`
- `updated_at: number`
- `ConfirmState` 统一为：
- `pending | answered | snoozed | expired | deduplicated`
- 状态语义固定：
- `pending` 仅用于主决策队列。
- `snoozed` 仅用于观察池。
- `expired` 表示长期无新证据后自动结束。
- `deduplicated` 表示被合并关闭。
- 默认生命周期：
- 新产生的 `watch` 项直接写成 `routing=watch, state=snoozed`。
- `snooze_until = now + 72h`。
- `expires_at = created_at + 14d`。
- 到期后不是直接重新进 `pending`，而是先重新评估。
- 若 72 小时后仍无新证据且仍属观察型，则延长 `snooze_until` 并累加 `snooze_count`。
- 若 14 天内没有新证据或风险升级，则自动转 `expired`。
- `high` 优先级、审批类、属性冲突类不自动过期，只允许提醒，不允许静默清掉。

### 4. 把去重从“文案去重”升级为“意图去重”
- 当前 dedupe 过度依赖 `question/context`，所以 “AI Notes Edit BE 的进展/负责人/上线时间” 会被当成多条。
- 去重键改为优先使用 `source_anchor + gapType`：
- 反射线程生成的项用 `thread:<threadId>`。
- ask 生成的项用 `ask:<requestId>`。
- outreach 生成的项用 `outreach:<sessionId>`。
- 属性类冲突保留 `entity/property` 锚点。
- 同一 `source_anchor + gapType` 下的新项只更新已有项的：
- `question` 取更清晰版本。
- `context` 取更丰富版本。
- `evidenceRefs` 合并。
- `updated_at` 刷新。
- `priority` 取更高值。
- 自动去重必须进入运行时：
- 创建时立即去重。
- heartbeat 每轮再对 `pending + snoozed` 做一次补偿去重。
- 现有 `dedupe-confirm-requests` 脚本保留为一次性修复工具，不再依赖人工执行。

### 5. 主决策中心改成“两层队列”，不再只显示一坨 pending
- `DecisionCenter.vue` 改为两个视图：
- `需你拍板`：只显示 `routing=decision, state=pending`。
- `待观察`：显示 `routing=watch, state=snoozed`，默认折叠，不计入主标题数字。
- 主标题数字只统计真正待拍板项。
- 每张卡必须显示“为什么来到这里”：
- 例如 `需要审批`、`需要你选方向`、`只是观察项`、`等待更多证据`。
- 去掉对 `evidence_resolution` 的固定三按钮默认模板。
- `decision` 卡的按钮必须与后续动作一一对应。
- `watch` 卡只提供轻操作：
- `立即查证`
- `继续观察`
- `结束追踪`
- 观察池支持按主题聚合，默认同主题只展开 1 张卡，避免 “AI Notes Edit BE” 这种重复淹没界面。

### 6. 现有 53 条做一次后台回收与重分流
- 新增一次性 migration/backfill 任务：
- 读取全部 `pending + category=evidence_resolution + priority=normal`。
- 用新的 disposition 规则重跑分类。
- 绝大多数直接改为 `routing=watch, state=snoozed`。
- 明显重复项做合并，保留最早 canonical。
- 仅保留确实需要你拍板、且有明确后续分支的项在 `pending`。
- 这一步不碰 `property_change`、`profile_conflict`、`openclaw_delegation` 之类高价值确认项。

## Public Interface Changes
- `GET /confirm-requests` 新增 `queue=decision|watch|all`，默认 `decision`。
- 响应新增：
- `routing`
- `reasonCode`
- `sourceAnchor`
- `updatedAt`
- `POST /confirm-requests/:id/answer` 仅用于真正的 `decision` 项。
- 新增 `POST /confirm-requests/:id/state`，用于：
- `pending -> snoozed`
- `snoozed -> pending`
- `snoozed -> expired`
- 前端 `ConfirmRequest` 类型同步扩展 `routing | reasonCode | sourceAnchor | updatedAt`。
- `ConfirmState` 类型补齐 `deduplicated`，与后端真实状态保持一致。

## Test Plan
- 单测：`EvidenceResolutionPlanner` 对“未来是否会变化/是否有计划”输出 `watch`，对“有 artifact 可查证”输出 `auto_verify`，对审批类输出 `decision`。
- 单测：同一主题的多种问法（如 AI Notes Edit BE）按 `source_anchor + gapType` 合并为一条。
- 单测：`watch` 项创建即为 `snoozed`，72 小时后重评，14 天无新证据自动 `expired`。
- 单测：高优先级审批类不会被自动过期。
- API 测试：`queue=decision` 不返回观察项；`queue=watch` 不返回待拍板项。
- UI 测试：决策中心标题数字只统计 `decision/pending`；观察池折叠且不污染主队列。
- 回归测试：`property_change`、`profile_conflict`、`openclaw_delegation` 的现有行为不变。
- 回收任务测试：现有 backlog 重分流后，不会误关闭真正的高价值确认项。

## Assumptions And Defaults
- 本轮优化默认先覆盖 `evidence_resolution`，其他高风险确认类型保持人工优先。
- 允许系统对低风险项做只读自动查证，不自动做外部写入或审批类动作。
- 观察池是二级视图，不计入主决策数量。
- 默认时钟策略固定为：`72h` 进入下一次重评窗口，`14d` 无新证据自动过期。
- 这次不靠“限制 pending 数量”解决问题，而是靠“入口分流 + 意图去重 + 生命周期管理”把错误进入主队列的项挡在外面。
