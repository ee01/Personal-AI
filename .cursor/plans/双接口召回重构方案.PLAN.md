# 双接口召回重构方案

## Summary

将“召回”明确拆成两类 HTTP 能力，并按场景分工：

- **被动联想接口**：新增 `POST /context-recall`
  面向网页 / 会议 / popup 这类被动触发场景，目标是快、准、结果少。只做高置信召回和轻量展示，不做 LLM 分析。
- **主动检索接口**：保留并升级 `POST /recall`
  面向 `ask`、记忆探索、分析型 UI、内部研究流程。返回原始证据 + 结构化 blocks，允许 timeline / table / chart / media 等 richer 结果，响应时间可比被动接口更宽松。

`/ask` 不作为第二个“召回接口”，而是继续作为问答编排层；它改为依赖升级后的主动 `/recall` 能力，而不是自己单独拼检索上下文。

## Interface Changes

### 1. 新增被动联想接口 `POST /context-recall`

请求体改成结构化上下文，而不是 `title + snippet` 的扁平 contract：

- `surface`
  `web_passive | meeting_passive | popup_passive`
- `contextType`
  `webpage | meeting | message_thread | jira_issue | document`
- `title`
- `url`
- `primaryText`
  当前最能代表上下文的文本，禁止直接塞整页 DOM 垃圾
- `secondaryTexts`
  最近消息、summary、topic、speaker、participants 等弱信号
- `entityHints`
  Jira key、人名、项目名、群组名等
- `scope`
  `work | personal | both`
- `sourceTypes`
  可选，前端可建议，后端按 surface 仍有默认约束
- `limit`
  默认按 surface 控制，一般 1-3

响应体只返回轻量高匹配结果：

- `matches`
  每项包含 `id / score / title / snippet / sourceLabel / sourceUrl / sourceTitle / links / whyMatched`
- `topMatch`
  方便网页 bubble / meeting danmaku 直接消费
- `queryTimeMs`
- `debug`
  仅调试模式返回归一化 query 和命中渠道

默认策略：

- 不调用 LLM
- 默认只走 `vector + fts`
- 先粗召回，再做轻量二次重排
- 返回 1-3 条，优先带 1-2 个可直接打开的源链接
- 对 UI 文案、导航文案、按钮文本、短模板句做强降权或直接拒绝

兼容策略：

- 现有 `/context-match` 保留一段兼容期
- 内部实现改为适配新 `context-recall` 服务层
- 旧 `title/keywords/snippet` 请求只做兼容映射，不再继续扩展

### 2. 升级主动检索接口 `POST /recall`

保留 `/recall` 路径，但从“证据列表接口”升级为“主动研究接口”。返回结构采用 **blocks**，同时保留原始 evidence 兼容旧调用。

请求体新增：

- `responseMode`
  `evidence | hybrid | blocks`
- `analysisMode`
  `search | research | aggregate`
- `blockTypes`
  `summary | timeline | table | chart | evidence_list | media`
- `presentationHint`
  从当前 `default | compact | meeting_pilot` 扩成更通用的 active 展示 hint

响应体升级为：

- `items`
  继续保留，作为原始 evidence 列表
- `blocks`
  稳定 block schema，供 ask / UI 直接渲染
- `analysis`
  结构化检索总结、聚合说明、排序理由
- `artifacts`
  多模态或外部资源引用，使用 URL / file ref / structured spec，不在 v1 强制生成图片
- `queryTimeMs / channels / totalFound`

block schema 在 v1 只定这几类：

- `summary`
  文本总结与关键结论
- `timeline`
  有序事件列表
- `table`
  `columns + rows`
- `chart`
  `chartType + labels/series` 或等价 spec
- `evidence_list`
  精选证据卡片
- `media`
  链接、附件、截图、PDF、页面卡片等引用信息

兼容策略：

- `responseMode=evidence` 时，保持当前 `/recall` 旧调用几乎不需要改
- `responseMode=hybrid` 时，同时给 evidence 和 blocks
- `responseMode=blocks` 时给面向 UI 的研究结果
- 这样内部工具和自动化逻辑可以继续低成本使用 `/recall`，而 ask / memory-exploring / dashboard 再逐步吃 richer 结果

### 3. `/ask` 调整为主动召回编排层消费者

`/ask` 与 `/ask/stream` 继续保留，但内部不再自己拼“检索上下文字符串 + LLM”。改为：

- 先调用主动 `/recall` 对应的服务层，使用 `responseMode=hybrid`
- 直接拿 `items + blocks + analysis` 作为生成输入
- 输出仍保留 `answer / evidence / structuredAnswer / externalEvidence`
- 后续逐步让 `structuredAnswer` 与 `blocks` 对齐，减少重复 schema

默认做法：

- `structuredAnswer` 兼容保留
- `blocks` 作为新的主结构化载体
- `/ask` 返回中可附带 `blocks`，供桌面端和扩展 UI 直接复用

## Implementation Changes

### 1. 后端分层

新增两层服务，而不是继续把逻辑堆在 route 里：

- `ContextRecallService`
  负责被动联想场景的 query 组装、默认 source/channel 策略、轻量重排、精简输出
- `ActiveRecallService`
  基于 `RecallEngine` 做二阶段研究整理，生成 blocks / analysis / artifacts

`RecallEngine` 继续做第一阶段统一检索核心：

- 多通道召回
- 过滤
- 去重
- MMR 重排
- access reinforce

新增二阶段逻辑：

- 被动接口：高精度轻量 rerank
- 主动接口：研究型 rerank + 聚合 + block 生成

### 2. 调用位置迁移

**被动联想调用点**

- 网页右下角 bubble：当前 `contentScriptWebIntelligence -> background -> /context-match`
  迁到 `CONTEXT_RECALL_REQUEST -> /context-recall`
- Meeting Pilot 会中 memory refs：当前 `meeting-shell/background.ts` 直接 `client.recall(...)`
  改成使用 `/context-recall`
- popup：当前没有直接的被动联想 API 调用
  如果要展示“当前上下文相关记忆”，默认复用被动接口，不单独设计第三套逻辑

**主动检索调用点**

这些继续走 `/recall`，但分阶段迁移到新的 `responseMode`：

- `memory-exploring-messageHandler`
  搜索、时间线、实体页先用 `hybrid`
- `dashboardIntegration`
  先保留 `evidence`，后续吃 `blocks`
- `agentThinking / agentWorkflow / proactive-notifications / WebIntelligenceAnalyzer`
  先保留 `evidence`
- `FollowThreadHandler`
  仍使用 `evidence`，不强制接 blocks
- `/ask`
  改用主动召回服务层，默认 `hybrid`

### 3. 前端上下文采集重构

前端不能再直接传原始 DOM 文本，必须先做 surface-specific extractor。

网页侧：

- 为 `generic webpage / jira issue / doc / ringcentral message thread` 分别抽取 `primaryText`
- 把导航、按钮、壳子、固定文案排除
- `entityHints` 从 Jira key、人名、项目名、URL path 中提取

Meeting Pilot：

- 被动联想 query 只使用：
  - 当前 topic / current chapter
  - summary
  - 最近 4-8 条 transcript
  - speaker / share 状态
- participants 仅作为弱信号
- 会议页不再走通用网页 context chain

popup：

- 默认只消费已经存在的被动结果或按需触发被动接口
- popup 中真正的搜索/追问仍走主动 `/recall` 或 `/ask`

## Test Plan

### 被动接口

- 普通网页正文明确时，能命中高相关记忆，并返回精简链接
- 只有 UI 文案或标题过弱时，返回空，不硬匹配
- RingCentral meeting 页面不会再走通用网页联想逻辑
- Meeting Pilot topic 变化后，联想结果同步变化
- 同一上下文多次请求命中缓存；切换上下文后缓存失效正确
- `sourceTypes` 放开后，`web_passive` 依然只返回少量高置信结果

### 主动接口

- `responseMode=evidence` 保持当前旧调用兼容
- `responseMode=hybrid` 同时返回 `items + blocks`
- `timeline / table / chart / media` block schema 稳定，前端可直接渲染
- `/ask` 迁移后，`answer` 与 `evidence/blocks` 语义一致
- 内部 automation 类调用不会因 block 引入而显著增慢或破坏旧逻辑

### 兼容与迁移

- `/context-match` 兼容映射到新被动服务后，旧网页调用仍可工作
- 旧 `/recall` 客户端在不传 `responseMode` 时仍能收到可用结果
- 扩展端、memory-service 端、desktop-app 端类型同步更新后编译通过

## Assumptions

- 双接口定义为：`/context-recall` 负责被动联想，`/recall` 负责主动研究型检索。
- `/ask` 继续是问答编排层，不算第三个召回接口。
- 主动接口的多模态在 v1 以 **block + artifact ref** 为主，不要求服务端直接渲染 PNG 图表。
- popup 默认归入被动联想场景；只有用户进入搜索/深挖时才切换到主动接口。
- 内部 `RecallEngine.recall()` 作为后端底层能力保留，不要求所有内部代码都改成走 HTTP 新接口。
