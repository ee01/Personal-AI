# 消息反应新增“联动操作”入口与“关联操作”设计收敛

## Summary
- 在消息悬浮工具栏中新增 `联动操作` 按钮，作为最右侧功能按钮，位于 PAI 图标之前；它复用现有 `background -> pending config -> topic-modal` 链路，直接打开“记忆入口规则”弹窗并预填一条新规则。
- 规则页里原“自动化动作”统一改名为 `关联操作`。这是用户心智；底层字段继续保留 `automationPrompt` / `automationRequiresApproval`，不做存储 schema 迁移。
- AI 建议采用“`用户已有规则优先 + 样例库兜底约束`”方案，不依赖实时读取 OpenClaw MCP 能力。这个方向和官方产品的共性一致：消息上下文触发、模板化起步、自然语言创建但受控于已知动作族，例如 [Slack shortcuts](https://slack.com/help/articles/360057554553-Use-shortcuts-to-take-actions-in-Slack)、[Slack workflow templates](https://slack.com/help/articles/31449260577043-Build-a-workflow--Use-a-workflow-template)、[Zapier Copilot quick start](https://help.zapier.com/hc/en-us/articles/22234847450893-Zaps-quick-start-guide)。

## Public Interfaces / Types
- `EnvConfig` 新增 `ENABLE_LINKED_ACTION`，默认 `true`。
- 同时把消息交互配置模型收敛成完整一套可持久化按钮配置：`ENABLE_SNOOZE`、`ENABLE_FOLLOW_THREAD`、`ENABLE_AUTO_REPLY`、`ENABLE_LINKED_ACTION`。当前 `enableFollowThread` 只在工具栏里使用、未完整持久化，这次一并补齐。
- Background 新增消息类型 `OPEN_LINKED_ACTION_CONFIG`，payload 结构与自动答复一致：`sender`、`groupId`、`groupName`、`content`、`messageId`、`timestamp?`、`messageLink?`。
- `topic-modal` 新增 `pendingLinkedActionConfig` 启动逻辑；不新增新的规则存储字段，继续写入 `TopicItem.automationPrompt` 与 `automationRequiresApproval`。
- 新增一个内部建议生成模块，例如 `generateLinkedActionSuggestion()`；输入是消息上下文、用户已有 `automationPrompt` 历史、样例目录、配置状态；输出是一条建议文案和可选的样例来源标记。这个输出不必持久化为新 schema。

## Key Changes
- 消息工具栏与设置
- 工具栏顺序固定为：`稍后处理(icon)`、`关注后续`、`自动答复`、`联动操作`、`PAI 图标`。`联动操作` 继承当前自动答复的红色；`自动答复` 改为琥珀/橙色；`关注后续` 保持紫色；`稍后处理` 从文字改成闹钟 icon，点击仍默认创建 1 小时提醒，hover 仍展开快速菜单。
- `联动操作` 是独立全局开关，加入 Options 的“消息交互功能”区和悬浮设置弹窗。设置弹窗不再只管 snooze/auto-reply，而是完整反映所有已渲染按钮。
- `MessageReactionUI.ts` 视为 source of truth；若旧的 `SnoozeUI.ts` 仍被构建链引用，再同步修改，否则不继续双写 toolbar 逻辑。

- 从消息上下文打开规则弹窗
- 点击 `联动操作` 后复用现有 popup 打开方式，落一个 `pendingLinkedActionConfig` 到 `chrome.storage.local`，再打开 `topic-modal.html`。
- 预填规则沿用自动答复的匹配结构：`text` 默认用“发送了内容与以下语义相似：…”；`filterSender`、`filterGroup` 直接从当前消息带入；默认只开启“写入记忆 + 关联操作”，不自动打开通知、自动答复、关注后续。
- 弹窗打开后异步生成一条“关联操作”建议，生成过程不阻塞表单显示；给出 loading、失败兜底和“重新建议”按钮。

- 关联操作建议生成
- 主约束来源采用“用户历史优先”：优先参考用户当前已保存、最近创建/编辑的 `automationPrompt` 文案；如果没有足够历史，再退回内置样例目录。
- 样例目录不是展示文案集合，而是能力护栏。每条样例至少带：`sampleId`、`actionFamily`、`targetSystem`、`canSchedule`、`examplePrompt`。首批样例覆盖：转发消息给某人、给 Jira ticket 加 comment、写入表格、设置 Glip 状态、创建日程/提醒。
- 生成 prompt 时同时喂给模型配置信号，例如 OpenClaw 是否启用、Jira 是否已配置、Memory Service 是否可用；不做 OpenClaw 实时能力探测，因为这在当前系统里不稳定且不可依赖。
- 生成结果只填一条可编辑建议，不自动生成结构化步骤。规则卡片里的执行摘要继续由后端 RuntimeAction 规划结果负责展示。

- OpenClaw 禁用态与文案
- 规则页用户文案统一从“自动化动作”改为“关联操作”；按钮名称保留 `联动操作`，表达“从消息出发联动创建一条规则”。
- 如果 OpenClaw 未启用或关键配置不满足，`关联操作` 文本框禁用，并在其上方/其上层显示遮罩提示与 CTA，跳转到 Options 的 `#OPENCLAW_ENABLED` 区域。
- 实时移除遮罩使用现有 `chrome.storage.onChanged` 监听 `envConfig`，不使用 `localStorage.onchange`。用户在 Options 配好 OpenClaw 后，弹窗应立即解除禁用；如果文本框仍为空，则自动触发一次建议生成。
- Options 中 OpenClaw 文案要从“仅自我反思外部委派”更新为“自我反思与关联操作的外部执行入口”。

- 执行架构与 planner 复用
- 这轮采用“预分发层”思路，但不把 message-rule planner、reflection planner、dreaming 合并成一个大 planner。它们的输入和目标不同：`MessageRuleAutomationPlanner` 是“消息命中后怎么做”，`EvidenceResolutionPlanner`/reflection 是“证据不足时该查证/确认/外问什么”，`GenerativeReplay` 是周级洞察，不属于同类。
- 现有可复用的是底层执行语义，而不是 planner 本身：`ActionExecutor`、`delegate_openclaw` 审批策略、`create_confirm_request` / `ask_external_user` / `notify_user` 这些动作族选择模式已经存在。
- 因此本次只抽一个轻量共享层，例如“动作族/执行目标解析 helper”。`关联操作` 在用户侧仍是自然语言；message-rule planner 内部先尝试映射已知动作族，再决定走内部动作还是 `delegate_openclaw`。v1 不强行新增 Glip 直连执行器；Glip 相关副作用仍默认通过这层分发后落到 OpenClaw 或现有内部动作。
- 这能给后续一方执行器留槽位，但不会把当前故事扩大成“重写所有 planner”。

- 文档与命名
- 更新消息反应文档：消息工具栏从“稍后处理 + 自动答复”升级为四个入口，并明确 `联动操作 -> 记忆入口规则 -> 关联操作` 的默认流程。
- 同步更新相关文档中的用户表述：规则页叫“记忆入口规则”，能力项叫“关联操作”，不再对用户暴露“自动化动作（OpenClaw，可选）”旧文案。

## Test Plan
- 工具栏渲染测试：按钮顺序、颜色、闹钟 icon、`联动操作` 位于图标前最右侧功能位；全关时工具栏隐藏；四个开关分别生效。
- Background / modal 流程测试：点击 `联动操作` 会写入 `pendingLinkedActionConfig` 并打开规则弹窗；弹窗正确预填 `text`、`filterSender`、`filterGroup`。
- 建议生成测试：有历史规则时优先引用历史风格；无历史时回退样例目录；OpenClaw 未配置时不生成或不填充建议，配置完成后自动恢复并可生成。
- 禁用态测试：OpenClaw 未启用时文本框 disabled、遮罩和 CTA 可见；修改 Options 后通过 `chrome.storage.onChanged` 实时解除。
- 兼容性测试：旧规则仍正常显示；`automationPrompt` 和 `automationRequiresApproval` 的导入导出不受命名变更影响。
- planner/执行回归测试：新增入口不会改变现有自动答复、关注后续、稍后处理行为；message-rule planner 继续能消费 `automationPrompt`，只是 UI 入口变多。

## Assumptions / Defaults
- `联动操作` 是消息反应入口名，`关联操作` 是规则编辑页里的能力名；两者不强行统一成一个词。
- `自动答复` 新颜色默认改为琥珀/橙色；`联动操作` 保留现有红色。
- v1 不做 OpenClaw 动态 capability discovery，也不读取 memory-service 的实时能力清单；能力约束来自“用户历史 + 内置样例目录 + 已知配置状态”。
- `MessageRuleAutomationPlanner` 与 reflection/dreaming 不合并；只复用执行语义和必要的动作族解析 helper。
- 若 `SnoozeUI.ts` 已不在主链路中，不把它当维护目标；只在构建仍引用时同步更新。
