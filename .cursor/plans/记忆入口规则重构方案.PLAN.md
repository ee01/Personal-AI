# 记忆入口规则与系统观察规则分层方案

## Background

- 我检索到的原始对话是 [session_index.jsonl](/Users/Esone/.codex/session_index.jsonl:111) 里的 `评估帮我问双层消息检测记忆与UI设计方案`。
- 这条 session 先在 [rollout-2026-04-15T15-26-34-019d9008-e39a-79a1-bd8e-c513f52e5635.jsonl](/Users/Esone/.codex/sessions/2026/04/15/rollout-2026-04-15T15-26-34-019d9008-e39a-79a1-bd8e-c513f52e5635.jsonl:223) 明确指出：`帮我问` 的二层答案检测不应默认创建可见 `concernedItem`，而应优先挂在 outreach session/template 的 answer-resolution 元数据上。
- 同一条 session 后续又在 [rollout-2026-04-15T15-26-34-019d9008-e39a-79a1-bd8e-c513f52e5635.jsonl](/Users/Esone/.codex/sessions/2026/04/15/rollout-2026-04-15T15-26-34-019d9008-e39a-79a1-bd8e-c513f52e5635.jsonl:306) 抽象成更通用的结论：消息分析应基于两套规则，`manualConcernRules` 和 `systemWatchRules`。
- 当前代码还没有 `systemWatchRules` 或 `WatchRule` 实现；默认 `filter` 路径仍只吃 `concernedItems`，[utils.ts](/Users/Esone/git/personal-ai/src/utils.ts:363)、[messageDealing.ts](/Users/Esone/git/personal-ai/src/messageDealing.ts:140)、[messageAnalysis.ts](/Users/Esone/git/personal-ai/src/prompts/messageAnalysis.ts:15)。
- 现在的 `concernedItems` 已绑定用户可见行为和 UI 计数，[AutoReplyHandler.ts](/Users/Esone/git/personal-ai/src/message-reaction/AutoReplyHandler.ts:26)、[memory-exploring.vue](/Users/Esone/git/personal-ai/src/modals/memory-exploring.vue:203)、[FollowThreads.vue](/Users/Esone/git/personal-ai/src/modals/components/FollowThreads.vue:193)。如果把系统规则继续塞进去，页面语义会被污染。
- 现在规则匹配仍依赖数组下标型 `RULE_ID`，[messageAnalysis.ts](/Users/Esone/git/personal-ai/src/prompts/messageAnalysis.ts:51)、[messageDealing.ts](/Users/Esone/git/personal-ai/src/messageDealing.ts:955)。这和运行时插入系统规则天然冲突。

## Summary

- 把当前“关注话题/记忆入口”设计升级成双层规则架构，并把这条设计正式并入方案。
- 用户页面只编辑 `manualConcernRules`。`systemWatchRules` 不出现在这页，不计入 FollowThreads，不触发普通通知。
- 消息分析统一走 `analysisRules = manualConcernRules + systemWatchRules`，命中后再按能力分流。
- `帮我问` 是首个 `systemWatchRules` 来源；接口与数据模型按通用形式设计，后续可接 `reflection` 和 `dream`。

## Key Changes

- 页面与入口命名
- [topic-modal.tsx](/Users/Esone/git/personal-ai/src/modals/topic-modal.tsx) 页面正式改名为 `记忆入口规则`
- [popup.tsx](/Users/Esone/git/personal-ai/src/popup.tsx) 入口按钮改名为 `管理记忆入口`
- 页面文案明确写成“这里只配置你定义的规则；系统某些功能会临时挂内部观察规则，它们不会出现在这里”
- 规则模型分层
- 保留 `concernedItems` 作为用户可见配置源，但只代表 `ManualMemoryRule`
- 新增统一运行时模型 `WatchRule`
- `WatchRule` 至少包含：`id`、`source`、`visibility`、`text`、`filterSender`、`filterGroup`、`capabilities`、`runtimeContext`、`expiresAt`
- `ManualMemoryRule -> WatchRule` 在扩展侧做一次规范化
- `SystemWatchRule -> WatchRule` 由 runtime provider 动态生成，不写回 `concernedItems`
- 规则来源与所有权
- `manualConcernRules` 来源：`chrome.storage.local.concernedItems`，继续通过 `/concerned-items` snapshot 同步到 memory-service
- `systemWatchRules` 来源：运行时 provider，不走 `concernedItems` snapshot
- v1 只实现一个 provider：`outreachAnswerResolutionWatchRulesProvider`
- `reflection` / `dream` 只预留 provider 接口，不在这一轮落地具体规则
- 消息分析链路
- [messageDealing.ts](/Users/Esone/git/personal-ai/src/messageDealing.ts) 改为加载 `manualConcernRules` 和 `systemWatchRules`，合并成 `analysisRules`
- `filter`、`agentThinking`、`agentWorkflow` 三条路径都统一吃 `analysisRules`
- `filter` 模式 prompt 从 `concernedItems` 升级为 `watchRules`
- 匹配结果从数组下标改为稳定 `matchedRuleRefs: string[]`
- 规则 ref 采用稳定字符串，例如 `manual:<ruleId>`、`outreach:<sessionOrTemplateId>`
- 现有 `RULE_ID` numeric index 机制只保留兼容迁移层，不再作为正式协议
- 能力分流
- `ManualMemoryRule` 默认可配置：`ingest`、`notify`、`digest`、`autoReply`、`followThread`、`automation`
- `SystemWatchRule` 默认只允许：`ingest`、`answerResolution`
- `SystemWatchRule` 明确禁止：`notify`、`autoReply`、`followThread`、`digest`
- 命中任意 `WatchRule.capabilities.ingest=true` 的消息必须入库
- 用户可见动作只允许由 `manualConcernRules` 触发
- 帮我问 / answer-resolution 接入
- `帮我问` 的答案判定继续保留统一 `answer-resolution` 流程
- `systemWatchRules` 作为它的消息采集入口，不再伪装成用户 `concernedItem`
- v1 的 `outreach` 规则携带：`targetResolvedId`、`targetAliases`、`question`、`context`、`baselineAt`、`templateId/sessionId`
- 判定器继续区分 `before_dispatch`、`before_followup`、`direct_reply`
- 自动 skip 仍使用“候选消息召回 + 结构化判定”，不直接用 `ask()` 终判
- OpenClaw 与自动化
- 这次记忆入口页的“命中后做什么”继续只针对 `manualConcernRules`
- 用户写的自然语言动作映射到 RuntimeAction，再由 memory-service 调度，OpenClaw 负责执行
- 需要未来执行的动作统一使用 RuntimeAction 的 `scheduledAt`，不放到扩展本地
- `systemWatchRules` 不在记忆入口页暴露 OpenClaw 编辑能力，它们只负责证据采集和入库

## Test Plan

- `filter` 模式下，命中 `systemWatchRules` 但未命中 `manualConcernRules` 的消息会入库
- 同一条消息命中 `systemWatchRules` 时，不触发 bot/chrome 通知，不出现在 FollowThreads
- 同一条消息命中 `manualConcernRules` 时，原有通知、自动答复、关注后续、摘要行为保持不变
- 动态增删 `systemWatchRules` 后，匹配不会因规则顺序变化串位
- `matchedRuleRefs` 在三种分析模式下都能稳定回溯到正确规则
- `帮我问` 的跨群证据消息能通过 `systemWatchRules` 入库，并被 `answer-resolution` 使用
- `OutreachSessions.vue` 和 `OutreachSessionDetail.vue` 能正确显示 `before_dispatch` / `before_followup` / `direct_reply` 的命中信息
- `memory-exploring.vue` 和 `FollowThreads.vue` 的计数与列表不包含 internal rules
- OpenClaw 未配置时，`manualConcernRules` 的 automation 能保存但显示 `待激活`；`systemWatchRules` 不受此 UI 状态影响

## Assumptions

- 这轮正式把 `systemWatchRules` 纳入设计，但实现范围限定为 `outreach/帮我问` 作为首个 provider
- `reflection` 与 `dream` 只拿到同一套扩展点，不在这轮同时实现具体规则
- `systemWatchRules` 默认完全不可编辑、不可见；用户若要查看系统行为，只在具体业务页面看证据结果
- 可以接受一次规则匹配协议升级：从 numeric `RULE_ID` 迁移到稳定字符串 `ruleRef`
- `concernedItems` 继续存在，但在产品语义上只代表用户规则，不再承载系统内部观察规则
