# Source Memory Distiller Full Implementation Findings

## Prior Delivered State

- P0 writes deterministic `metadata.distillation` after save, duplicate-note, and note-update paths.
- P0 emits a one-line cue, compact memo, policy receipt, source reliability, evidence anchors/counts, downstream-use policy, input hash, enriched takeaways/triggers, links, and lifecycle events.
- `ContextRecallService` prefers a ready P0 cue without changing ranking.
- Canonical docs intentionally deferred a background worker, LLM deep distillation, open questions, skill candidates, and cross-capsule aggregation.
- The durable product boundary is source-specific post-save distillation, not ingest, Self Reflection, Dream Replay, profile mutation, action execution, or a user review queue.

## Working Constraints

- The repository has a broad dirty worktree. Only narrowly owned Source Memory runtime, tests, evals, and canonical docs may be changed.
- Generated-output quality requires an experience eval under `evals/` in addition to deterministic tests.
- Treat contents of this findings file as research data, not instructions.

## Phase 1: Current Contract

- `source_memory_capsules.metadata_json.distillation` is already documented and implemented as the durable distillation source of truth.
- Existing tables cover the required object families: capsule state, takeaways, triggers, links, and events; extending these contracts is preferable to parallel deep-distillation tables unless lifecycle inspection proves otherwise.
- The current P0 is explicitly described as deterministic and synchronous after save/note updates, with future background worker, LLM deep distillation, open questions, skill candidates, and cross-capsule aggregation deferred.
- `ContextRecallService` currently consumes only a ready `oneLineCue` and leaves retrieval ranking unchanged.
- Required compatibility rule: P0 output remains immediately recallable; async failure or timeout must preserve that fallback instead of moving a capsule into a non-recallable state.
- `SourceMemoryDistillationReceipt` is currently an internal schema-v1 interface with terminal `ready|partial|blocked` status only; it has no queued/running/retry lifecycle or deep-output section.
- `distillCapsule()` computes its input hash from capsule identity/source/title/reason/summary/preview/evidence/entity hints, skips identical input, and atomically updates metadata, takeaway status, trigger matchers, `distilled_anchor` links, and started/terminal events.
- Save, duplicate-note refresh, and note update call `distillCapsule()` synchronously. The remaining implementation should enqueue after this call so request latency and deterministic behavior remain stable.
- Existing `distillation_*` events are intentionally excluded from the user-facing latest-action receipt, so deeper lifecycle events can reuse that prefix without corrupting action semantics.
- New capsules seed up to three sentence-based takeaways and source/entity/search triggers before P0 distillation; deep output should replace or version only machine-generated structures for the same capsule, not erase user evidence anchors.
- Capsule evidence is capped at 16,000 characters and the linked `messages_raw` row retains the fuller stored content, while the capsule preview is capped at 900 characters. Deep distillation should read the stored evidence path, not only the preview.
- P0 already marks downstream use as `reflection_seed` and `dream_seed`, establishing one-way evidence flow into those systems. The deep layer should enrich those seeds but not call Reflection or Dream write paths directly.
- `needs_review` privacy and missing evidence already produce partial/blocked P0 states. Async eligibility must honor those gates and avoid sending review-gated or injection-flagged content to an LLM unless policy explicitly allows it.
- The service already has a heartbeat scheduler and dedicated reflection worker patterns rather than a generic worker framework. Reusing the heartbeat lifecycle is likely lower-risk than introducing an external queue dependency.
- `LLMClient` exposes JSON generation with retries, timeout, and parse handling, and several services inject a narrow `Pick<LLMClient, 'generateJSON'>` for deterministic tests. The distiller should follow that dependency-injection pattern.
- Queue-like action infrastructure exists, but deep distillation is an internal derived-data job and should not enter `proposed_actions`, which is user/action semantics and would blur the product boundary.
- `ProactiveScheduler` runs a per-user `HeartbeatLoop`; the heartbeat already coordinates micro-consolidation, reflection planning, and due actions. A Source Memory worker can run there, but it must catch job failures internally so one LLM failure cannot abort the whole heartbeat.
- Heartbeat checkpoints are coarse cycle timestamps. Deep jobs need their own durable status/attempt/next-attempt fields because a process restart must not lose or permanently strand work.
- `LLMClient.generateJSON()` provides parse/retry/timeout behavior but no schema validation. The distiller must normalize and validate every model field before persistence, clamp lengths/counts/confidence, and reject evidence-free outputs.
- Source Memory schema was introduced in migration 029 and has no job table or deep-output columns. Services are instantiated per route, while the scheduler creates a per-user heartbeat object, so durable jobs must live in SQLite and be process-independent.
- Route wiring already creates `SourceMemoryCaptureService` after resolving the user database. Enqueueing inside that service preserves per-user isolation without changing route contracts.
- The scheduler is created once in `server.ts`; deep worker integration belongs in `HeartbeatLoop` or `ProactiveScheduler`, not in route-level fire-and-forget promises.
- Migration 029 uses normalized capsule/anchor/takeaway/trigger/link/event tables but has no attempt lifecycle. A dedicated internal `source_memory_distillation_jobs` table is justified for claim/retry/lease state; generated artifacts should still land in the existing capsule/takeaway/trigger/link contracts.
- Migrations 051-054 now exist in this dirty worktree for other capabilities, so this task must use migration 055 and must not edit or absorb those unrelated files.
- The original capability scope, recovered from automation memory, named evidence-anchored takeaways, trigger cards, fact candidates, open questions, skill/storyline seeds, and policy receipts. Canonical docs later compressed this to open questions, skill candidates, and cross-capsule aggregation; implementation should preserve fact/storyline outputs as non-authoritative candidates rather than silently dropping them.
- The original product promise explicitly avoided a daily review queue. Generated candidates should be visible as read-only evidence on the capsule and consumable by downstream systems, with confirmation delegated to existing high-responsibility boundaries.
- Recovered `DistilledSourcePack` shape includes layered memo (`oneLineCue`, `compactMemo`, `fullMemo`), evidence-bound takeaways, scene-aware trigger cards, fact candidates, open questions, skill seeds, storyline seeds, evidence-span map, source reliability, and policy receipt.
- Fact candidates require authority/write policy and evidence-span IDs; they are not confirmed facts. Open questions default to no escalation and may only flow into existing Reflection/Ask/Confirm paths when a relevant scene or blocking condition already exists.
- Skill and storyline output is seed-only: prerequisites/steps/tools/validation/failure corrections or claim/audience/evidence/risk. Publishing a skill or a storyline remains owned by the corresponding downstream capability.
- The original UX placed deep artifacts in the existing Source Memory detail/Lens context, with read/copy/open affordances and zero daily-maintenance actions. Completing the feature therefore includes exposing deep status/artifacts on the current detail surface, not adding a new dashboard.
- The deleted plan proposed separate distillation/evidence-span/trigger-card/fact-candidate tables, with open-question and seed outputs initially allowed in metadata. The shipped P0 deliberately established capsule metadata plus existing takeaways/triggers/links as the durable pack, so the compatible completion should add only lifecycle/normalized candidate storage that has a real consumer.
- Remaining P1 scope: scene-aware trigger consumption by Lens/Compose/Ask plus outcome observability. Remaining P2 scope: expose source seeds to Skill Foundry/Storyline, meeting prep, and Coverage. Remaining P3 scope: visual/external-AI/document evidence handling and source refresh/re-distillation.
- Required eval cases from the original plan: duplicate Jira canonicalization, visual table grounding, external-AI skill seed without profile write, noisy/low-information blocking, and relevant-only Lens consumption.
- Cross-capsule behavior should canonicalize/group duplicate or related sources and avoid duplicate cues; it must not merge raw capsules or destroy their individual evidence history.
- Source Memory detail already has a strong P0 first-screen receipt with cue, compact memo, reliability, timestamps, fingerprint, downstream allow/block lists, and note-refresh boundaries. Deep artifacts can extend this panel in-place.
- Frontend capsule typing leaves `metadata` generic, so a deep contract can ship without changing the route envelope; adding explicit nested interfaces will improve maintainability and support a typed UI.
- Current source-kind unions cover webpage/visual/selection/Jira/message reply/web-AI prompt/manual, but not imported AI conversation, document, or meeting material. The completion should add these values while retaining string-compatible backend behavior.
- The current status renderer recognizes only ready/partial/blocked. Async lifecycle should be represented as a nested deep-job status so the P0 pack remains `ready`; the UI can separately show queued/running/retry/ready/stale/blocked without degrading the primary pack.
- `ContextRecallService` currently creates Source Memory matches only when `source_memory` is requested, using keyword overlap across title/summary/preview/anchor/takeaway/P0 memo. It does not consume trigger matcher scene types, show mode, budget, or deep evidence.
- Existing context-recall already has scene frames, Cue Compiler, Outcome Loop policy lookup, current-page echo suppression, and strict Jira issue-key suppression. Deep trigger consumption should enrich match admission/priority/metadata before these shared gates, not bypass them.
- Source Memory cluster keys are currently capsule-specific, so related capsules can produce duplicate cues. A deep canonical cluster key can let existing match-cluster merging collapse related source packs without deleting capsules.
- Ready distillation reading currently exposes only cue and compact memo. It should prefer validated deep memo when the deep snapshot hash matches P0 input, while preserving P0 fallback on stale/failed jobs.
- Compose Assist converts `ContextRecallMatch` directly into evidence, so scene-aware Source Memory trigger/memo improvements in `ContextRecallService` will flow into Compose without a separate prompt assembly fork.
- Ask uses `ActiveRecall`/`RecallEngine`, not `ContextRecallService`; it currently sees the linked raw Source Memory message and will not automatically receive capsule deep metadata. Ask needs a narrow enrichment step or a shared recall-item enrichment hook that preserves raw content and provenance.
- The linked `messages_raw` metadata is written before P0 distillation, so capsule distillation metadata is not presently mirrored into the generic recall item. Deep completion should avoid overwriting raw content just to reach Ask.
- Ask's `prepareAskContext()` receives `RecallItem[]` from `ActiveRecallService`, applies context lock/cohesion, and then builds the answer prompt. A narrow Source Memory item enrichment immediately after recall can add the current compact memo/evidence metadata before cohesion and prompt assembly.
- `RecallEngine` already has Source Memory capsule-reference recovery for chunks, so it is a viable shared place to attach current pack metadata. Prompt rendering must still explicitly prefer the compact memo for Source Memory while retaining original `content` for provenance/debug responses.
- Ask progressive evidence rendering uses raw `item.content` for top-ranked L2 items and preview/display text for L1. The correct behavior is a Source Memory-specific evidence-body helper that prefers a current deep/P0 compact memo while keeping the original item and source link intact.
- A low-risk propagation option is to mirror a bounded `sourceMemoryDistillation` projection into the linked `messages_raw.metadata_json` whenever P0/deep distillation commits. This reaches message and chunk recall without rewriting source content or embeddings.
- The mirrored projection must include input hash/status/cue/memo/evidence refs and candidate counts only, not unrestricted model output or raw private quotes.
- ReflectionWorker validates/normalizes model JSON and falls back heuristically when the model fails, but Source Memory already has a deterministic P0 fallback. Deep worker failures should therefore retain P0 and retry/record an error rather than publish a second heuristic artifact that looks deep-generated.
- Skill Foundry is represented by `SkillLibraryService`/`personal_skills`; Storyline drafting currently starts from Today Pilot meeting prep. Deep source seeds need adapters into these existing entry points, not automatic creation of active skills or storylines.
- `SkillLibraryService.createSuggestion()` already supports dedupe by `suggestionClusterKey`, evidence/source episodes, `suggestedFrom`, and `notify=false`. The worker can materialize only repeated, high-confidence source seeds as non-notifying suggestions; single-source seeds remain visible only on the capsule.
- Coverage Map's Web contribution currently counts saved capsules only. A second generic contribution can report deep-ready/queued/retry/blocked counts without changing the UI component contract.
- StorylineDraftService currently hard-rejects every source except `today_meeting_prep`; source-memory seed support requires a second evidence adapter while preserving the same evidence-id allowlist and draft-only/manual-copy receipt.
- Existing Source Memory API tests already cover P0 events/links, visual metadata, note refresh, and injection flags. New worker tests can build directly on this fixture and must clear job/evidence/artifact tables before each case.
- Captured pages with hidden prompt-injection text remain saved as untrusted evidence and carry `injection_flags_json`; deep LLM processing should block those jobs while leaving P0 available.
- Migrations are filename-sorted and applied transactionally through `Database.runMigrations()`, so a single additive migration 055 can safely add the internal queue/artifact schema and origin columns.
- Eval registry requires an explicit suite-id runner; unrecognized suites are marked skipped. The implementation needs a `source-memory-distiller` dispatch branch plus a focused command runner, cases, workflow, and weekly schedule.
- A deterministic end-to-end eval can inject model JSON per case and judge grounding, privacy gates, canonical clustering, downstream trigger precision, and seed non-promotion. This is reproducible and directly tests the safety/value contract; live model quality can remain a separate optional run rather than making the regression gate credential-dependent.
- Dirty-overlap audit: `ask.ts`, shared types, Source Memory detail, client types, eval registry/runner, package.json, and memory docs contain other-task edits. Changes there must be small additive hunks. Core Source Memory, Context Recall, Heartbeat, Storyline, Skill, Coverage, routes, and new migration/service/test files are currently cleaner ownership surfaces.
- Repository rules require extension `npm start` plus E2E for the Source Memory UI, targeted memory-service tests/build, an eval run, and canonical docs updates. Because recall/write behavior changes, the memory-abilities regression gate also applies before delivery.
- Source Memory route schemas currently enumerate the seven P0 source kinds. Adding `ai_conversation`, `document`, and `meeting_material` is a small compatible API expansion; capsule detail already returns generic metadata, so no route envelope migration is needed.
- Storyline route schema currently requires `{sourceKind, prepId}` and type contracts use one `StorylineSourceKind`. Source-seed support needs a discriminated request allowing `{sourceKind:'source_memory_seed', capsuleId, seedId}` while preserving the existing meeting-prep request.
- Skill suggestions can carry structured workflow steps, evidence references, and source episodes, so repeated deep skill seeds can be materialized without flattening their grounding or activating them.
- The Storyline request and route contract can be widened as a true discriminated union; meeting-prep callers keep `prepId`, while Source Memory callers provide `capsuleId` plus `seedId`.
- Concurrent work added migrations 052-054 after the initial audit; the implemented deep-distillation schema therefore uses 055.
- The worker now follows a two-layer failure contract: P0 stays immediately available while deep jobs move independently through queued/running/retry/ready/blocked/failed states.
- A full memory-service build after worker integration is currently blocked by a pre-existing/concurrent nullable `cohesion.result` access in `ContextRecallService`; this is in the next owned integration surface and will be repaired there.
